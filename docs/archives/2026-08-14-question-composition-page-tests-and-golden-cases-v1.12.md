# 面试工作台组题页面回归与三类 Golden Cases V1.12

## 目标

在 V1.11 use-case hooks 边界稳定后，为尚未覆盖的本地规则组题和 DeepSeek 单题容错补页面级流程，并建立产品、运营、法务三类可重复的脱敏组题质量基线。

## 页面级回归

### 本地来源化组题

从带当前岗位 JD、脱敏简历和已归档面经来源的浏览器状态开始，用户点击“本地规则组题”后验证：

- 页面显示当前公司与岗位的生成结果；
- 简历题和专业／JD 题两个主类别都存在；
- 面经原题保留原文、`source_question` 和原来源 ID；
- 本地规则题显示正确来源标签；
- `questionsTargetKey` 和完整题库写入 localStorage。

### DeepSeek 单题容错

模拟本地桥接返回两道有效题和一条 `SOURCE_QUOTE_MISMATCH` warning，验证：

- 页面保留并展示两道有效题；
- 模型衍生题显示“DeepSeek 生成”，不冒充面经原题；
- 页面明确显示安全跳过 1 道异常题；
- 发给组题 client 的来源只有当前岗位来源，其他岗位来源不发送；
- 持久题库只包含有效题目。

该测试验证浏览器与桥接的部分成功契约，不绕过服务端已有的逐题来源校验。

## 三类脱敏 Golden Cases

fixtures 位于 `src/test/fixtures/question-composition-golden.ts`，全部为虚构公司、岗位和组合经历，不包含真实个人资料。

| 案例 | 重点能力信号 | 固定面经问题 |
|---|---|---|
| 产品 | 用户研究、需求判断、数据验证、跨团队交付 | 判断 AI 功能是真需求还是技术展示 |
| 运营 | 用户分层、漏斗分析、活动策略、增长与留存 | 曝光增长但转化下降时先检查什么 |
| 法务 | 合同审查、数据合规、知识产权、风险闭环 | 业务坚持高风险条款时如何推进决策 |

三类案例统一执行 9 条测试，覆盖：

- 两类主类别同时存在，总量保持 5–12 题；
- 标题不重复，每题只有一个问号，不生成 `coach_generated` 本地题；
- 每类生成 3 道简历题，逐字引文必须存在于简历；
- 至少命中一条与 JD 有明确能力词交集的高价值经历；
- 3 道简历题至少使用两个不同 `primaryProbe`；
- JD 推演题逐字引用当前 JD；
- 面经原题只有当前岗位的一道，原文、来源 ID 和类别保持不变；
- 其他岗位来源不会进入题库；
- 每道题都有材料来源。

## 测试发现

页面测试第一次运行时，通用脱敏简历夹具虽然文字说明称“足够长度”，实际不足产品要求的 80 字，页面正确阻止了组题。修复方式是补全脱敏经历，不放宽生产校验。

第二次运行时，测试把状态标为“手动整理”却期待保留已归档来源 ID；生产逻辑会按设计将手动正文重建为新的手动来源。测试随后明确改为 Agent 导入来源，保证测试语义与期望一致。

Golden 第一次运行有 8/9 通过；产品经历使用“用户访谈”而 JD 使用“用户研究”，未满足确定性词项交集。fixture 改成含义更明确的“用户研究访谈”后 9/9 通过，没有扩大匹配词表或放宽门禁。

## 可重复性边界

- Golden 自动门禁只运行确定性本地引擎，因此不需要网络、API Key 或模型调用。
- DeepSeek 单题容错页面测试使用固定桥接响应，验证的是安全协议和 UI 写回。
- 真实 DeepSeek 输出具有模型与时间波动，不作为唯一 Golden 答案。后续真实观察应记录问题类型，再把稳定规则沉淀为允许集合、确定性校验或新的脱敏 fixture。
